## HW-V2-02 — подготовка входа без датчика и кабеля

Завершена ограниченная документационно-расчётная итерация:
[независимый итог](docs/reviews/hw-v2-02-review.md), факты и следующий
шаг — [progress](docs/progress.md). Физическая готовность входа не заявляется.

Вход: `24cce1928e8a400010536bb38715e34948c17246`, работающий транспорт V2S4,
подтверждение пользователя: датчик и кабель пока не изготовлены; одиночный
ЛБП около 0…20 В, мультиметр/измеритель ёмкости, редкий доступ к осциллографу.
Уровень этой итерации — **документация и воспроизводимая идеальная модель**.
Результат — P1-LV, отдельный лабораторный DC-макет с однополярным питанием
для будущей проверки смещения/фильтра/шкалы; он не заменяет высокоомный P0.

Критерии готовности:

1. Сравнить P0 с преобразователем питания, P1-LV и активный пробник;
   обосновать ближайший ограниченный шаг, не понижая требования к датчику.
2. Описать P1-LV по узлам/выводам точного корпуса, номиналам и составу деталей;
   показать питание, разомкнутый выход к ADC, контрольные точки и тестовый
   источник от той же шины. Чертёж — расчётный, не PCB/не прошедшая ERC схема.
3. Воспроизвести DC-передачу, нагрузку/подпор на входе, номинальные коэффициенты,
   резисторные углы, идеальную частотную/ступенчатую характеристику и влияние
   неизвестных ёмкостей. Проверить сходимость численного расчёта; не выдавать
   модель за SPICE с реальными ОУ или измерение.
4. Зафиксировать план проверки с мультиметром и отдельный обязательный
   осциллографический этап до связи с ADC, границы питания/перегрузки/земель,
   критерии остановки и таблицу будущих измерений.
5. Обновить требования, решения, прогресс и устаревшее указание «измерить
   имеющийся кабель». Один независимый критик проверяет точный manifest
   по quality-gate; порог ≥9,5, без авторства реализации.

Не входят: подключение/перепрошивка платы, прошедшие физическую приёмку
диапазоны, калибровка реального CH1, окончательный вход зажигания, PCB,
закупка и цена. Следующая ступень — паспорт доступных деталей/приборов,
редактируемая электрическая CAD-схема и проверка монтажа; затем отдельный
низковольтный опыт. Отсутствие датчика не блокирует подготовку.

## V2-05: непрерывный приём STM32 — завершён ограниченный транспортный этап

Приёмка ограниченной области — [независимый итог V2-05](docs/reviews/v2-05-review.md);
фактические результаты и незакрытые ограничения — [progress](docs/progress.md).
Следующая задача V2-05a указана ниже; измерительная часть остаётся отдельным этапом.

Вход: принятый V2-04a (`a746825`), подтверждение пользователя о работающих
Record/Open, подключённая COM6 и ST-Link, сообщённый STM32F103C8T6,
неподключённый PA0. Одна ограниченная вертикальная цепочка: отдельный Connect
с HELLO/CAPS без START → явный поток CH1 → запись raw → Stop → fresh open.
Измерение напряжения, аналоговый тракт, зажигание и полная квалификация
прошивки в эту итерацию не входят.

1. Проверить опубликованный потоковый исходник, сохранить авторство и точную
   привязку. Считать нынешний образ для возврата без стирания/записи Flash.
2. Добавить реальный serial к существующим stream owners: единый владелец COM
   с оконным UI, отдельные Connect/Start, видимая несовместимость, UNKNOWN_PROFILE,
   происхождение device и наблюдённые CAPS отдельно от заявленного SHA.
3. Подготовить самостоятельную V2-сборку закреплённого runtime имеющимся
   Windows toolchain: ELF/map/BIN, границы 64 KiB Flash/20 KiB RAM,
   stack/ABI/IRQ/DMA/USB, новый build ID и хеши. Не переименовывать старый
   NEVER_FLASH ELF в разрешённый образ и не присваивать ему чужой provenance.
4. Независимый критик отдельно оценивает программный результат и допуск
   **точного** образа к короткому опыту транспорта на нынешней плате с пустым
   входом. Не требовать результатов первого опыта до его проведения и не
   выдавать этот ограниченный допуск за квалификацию прибора.
5. После допуска и готового возврата: записать/сверить образ, проверить реальный
   поток, штатный Stop, файл/Open и обработку разрыва. Сохранить исходные
   свидетельства; неизвестное produced_end не объявлять нулевыми потерями.
6. Собрать Windows-пакет и проверить изменённый UI; один независимый итог
   по quality-gate ≥9,5 для фактически подтверждённой области. Если аппаратная
   часть недоступна, явно сохранить незакрытый пункт и следующий шаг.

Только необходимые проверки изменённых границ. Фактические результаты и
неизвестные параметры — в [progress](docs/progress.md).

## V2-03a: сохранённая постановка закрытия с незавершённым окном

Ограниченное исправление поведения закрытия: неполное аппаратное окно не должно требовать обязательного сохранения JSON. Пользователь получает явный выбор для этого окна, а уже сохранённая `.mtv2` остаётся без изменений. Основание — [V2-DEV07](requirements.md), технический контракт — [device-connection.md](docs/device-connection.md). Пользовательский опыт с новым EXE и фактические результаты исправления фиксируются только в [progress.md](docs/progress.md).

Критерии готовности:

1. При закрытии с несохранённым незавершённым окном диалог предлагает «Сохранить JSON», «Закрыть без JSON», «Отмена»; безопасный выбор по умолчанию — «Отмена».
2. Успешное сохранение JSON позволяет продолжить закрытие. Отмена выбора файла или ошибка записи оставляет приложение открытым и сохраняет неполные данные в памяти.
3. «Закрыть без JSON» разрешает отказаться только от конкретного неполного окна, показанного в диалоге. Новые или заменившие его данные требуют отдельного решения; молчаливого общего сброса нет.
4. «Отмена» сохраняет приложение и неполные данные. Полные записи и ранее сохранённые файлы не изменяются ни одним из трёх вариантов.
5. Прежние Stop/reset/recovery и проверка остановки рабочего потока сохраняются; согласие не сохранять JSON не отменяет их. Только необходимые проверки трёх вариантов, отмены/ошибки сохранения и смены ожидающего окна; новое обращение к COM для этого исправления не требуется.
6. Независимый критик проверяет точное исправленное состояние по порогу ≥9,5/10, затем проверяется относящаяся к изменению новая сборка. До свидетельств план не считается выполненным.

Аппаратная настройка, калибровка, новый входной сигнал, изменения firmware/wire и непрерывная запись не входят в V2-03a. После передачи исправленного пакета следующий пользовательский шаг — повторить закрытие и выбрать нужный вариант сохранения неполных данных. HW-V2-01 остаётся отдельной последующей задачей.

## V2-03: сохранённая постановка совместимости STM32 и оконного подключения

Пользователь подтвердил работу приложения и попросил переход к STM32, начиная с совместимости. Границы итерации — [device-connection.md](docs/device-connection.md); фактический handshake, проверки и версия нового EXE фиксируются только в [progress.md](docs/progress.md).

Результат: прежний дизайн с отдельной панелью «STM32 · подключение», явным COM, HELLO/CAPS без ARM и отдельными Auto/Single/Stop. Основой остаётся оконный wire 0.1 и существующий `AcquisitionBridge` с worker, Stop/reset/recovery. Не импортировать PR #216/wire 0.2 и не перепрошивать плату в этой задаче.

Критерии ограниченной итерации:

1. Сверены точные опубликованные firmware/protocol, контракт и возможности сеанса. Известное расхождение приоритета malformed-команд во время Stop сохранено в документации; полная conformance не заявляется.
2. До явного подключения COM не открывается; Connect отправляет HELLO/GET_CAPS, не CONFIG/ARM. Start разрешён только при согласованном текущем CAPS. Отдельные кнопки запускают Auto-окна/Single и подтверждённый Stop.
3. `UNKNOWN_PROFILE` сохраняется: никакой автоматической шкалы U_CH1. Только явно включаемый служебный raw-график; порог 1…4094 код, предыстория из CAPS, без аппаратного holdoff.
4. Одно полное окно сохраняется в `.mtv2` и CSV/JSON со своим локальным временем и неизвестным промежутком до других окон. Неполные фрагменты — отдельный диагностический JSON. Continuous Record для устройства недоступен.
5. Сохранены честные ошибки подключения/Stop/закрытия, необходимость фактического reset и возврат в DEMO. Только целевые проверки нового адаптера/GUI; неизвестные аппаратные характеристики не подменяются тестами.
6. Независимый `requirements_audit` проверяет точную версию и доказательства по прежнему порогу ≥9,5/10. Затем новая сборка EXE проходит относящийся к изменению ограниченный smoke.

Первый пользовательский опыт использует существующее подключение платы без нового сигнала: Connect → прочитать CAPS → явно raw → Auto/Single → Stop → сохранить окно. Калибровка и допустимый DC-вход — следующий отдельный шаг, а не условие разработки соединения. Непрерывное сохранение аппаратного сеанса потребует отдельного сегментного формата/контракта времени.

4. В комплекте есть пользовательская инструкция, точные manifest/хеши, уведомления и список открытых пунктов аудита зависимостей/соответствующих исходников. Наличие notice-файлов не считается завершённым аудитом.
5. Независимый критик оценивает точную версию/пакет ≥9,5/10 по программной области; результаты публикуются в progress без переноса аппаратной готовности.

Чистая машина без Python, публичный релиз/подпись, реальное устройство и изменение измерительного тракта не являются выполненными фактами V2-02. Взятые сверх ограниченного smoke проверки назначаются только по обнаруженному дефекту. Следующая отдельная задача — V2-03, подтверждённый реальный источник с явным профилем входа.

## V2-01: сохранённая постановка первой рабочей итерации

Результат: самостоятельное настольное приложение в `host/` на Python/PySide6/pyqtgraph с оформлением по [пяти макетам](docs/design/README.md), одним CH1, профилями «Осциллограф» и «Зажигание», явным ДЕМО и шкалой напряжения на разъёме. Исходная опубликованная база — `3ebfe1479056d64ce9c4a1eadad048f60ade100f` ([выбор](docs/decisions.md)). Новая ветка — `ui-v2/initial-design`.

Входы: код выбранной базы; TXT редакции 5, раздел А и приоритет 4А; пять PNG и README редакции 4. Прошивка и реальная плата не нужны для разработки интерфейса и формата.

Проверяемые цепочки этой итерации:

1. ДЕМО → живой график в В/мВ → независимая пауза просмотра, масштаб и курсоры.
2. Переключение двух профилей → общий физический CH1; имя сохраняется между запусками. Синусоида/прямоугольный сигнал сохраняют DC-составляющую.
3. Однократный программный захват с предысторией → просмотр/сохранение. Поиск зажигания выдаёт кандидаты событий, без диагноза и автоматического «времени горения».
4. Record → ограниченная запись → Stop → сохранить → открыть → тот же raw, время и снимок пересчёта → экспорт CSV/JSON выбранного участка. Чтение вне GUI: `python -m motortester.v2.inspect PATH [--csv CSV] [--start-index N --stop-index N]`, [контракт](host/docs/v2-format.md).
5. Физический источник без известного тракта → понятное недоступное состояние и `unconfigured`, без выдуманного U_CH1.
6. Независимый критик проверяет точное состояние; исправления до порога по [quality-gate.md](docs/quality-gate.md).

Только необходимые проверки: известные примеры преобразования (включая отрицательный коэффициент), сохранение/открытие и ошибки файла, несколько сценариев состояний GUI, реальный скриншот запуска. Не запускать весь исторический firmware-набор для изменений GUI. Конкретные выполненные проверки и ограничения записываются в progress, отдельно от этого плана.

# Задача дипломного проекта

## Цель

Разработать MVP одноканального мотортестера: бесконтактный съём сигнала системы зажигания, регистрация осциллограмм на STM32F103C8T6 со встроенным АЦП, передача по USB и работа в приложении Windows 10. Текущий этап исключает ML и автоматическую диагностику; возможность их последующего добавления сохраняется.

Рабочее название: «Разработка микроконтроллерного мотортестера с компьютерным анализом сигналов системы зажигания».

## Приоритеты

1. Один сквозной работающий канал: захват, USB, график, Auto/Normal/Single, предыстория, файл и повторное открытие. Тёмный русский интерфейс и встроенная инструкция.
2. Полный комплект: исходники и воспроизводимые сборки firmware/Windows-приложения, схемы, расчёты, BOM, алгоритм, инструкция сборки/прошивки/запуска, документ и локальный сайт.
3. Реальная проверка на низком напряжении, затем на подготовленном стенде. Программную готовность отделять от аппаратной по [ТЗ MVP](docs/mvp-spec.md).
4. После основы: второй канал, собственная PCB, обработка/ML; G474, внешний АЦП, Ethernet и DIAMAG только при отдельном обосновании. Автомобиль не блокирует стенд.

Для MVP зафиксированы Blue Pill с STM32F103C8T6, встроенный АЦП и native USB. Ограничения будущего измерительного профиля определить в рамках этих ресурсов. Исходные условия — в [requirements.md](requirements.md), расчёты — в [архитектуре](docs/architecture.md), расходы — в [бюджете](docs/budget.md).

## Передача и очередь MVP — 10.10.2026

Текущая работа — согласованный по составу интеграционный черновик A. Опубликованные проверки отдельных компонентов не заменяют проверку этого снимка и приёмку MVP. Фактические шаги и проверки — в [progress.md](docs/progress.md), рецепты — в [object-сборке](firmware/build/README.md) и [static-link/export](firmware/build/BUILD_IMAGE_README.md). Проект остаётся **BLOCKED_EVIDENCE, score:null**; локальные scoped-вердикты не закрывают приёмку MVP. **DOC-005** — историческая документационная итерация передачи. Основной Dot получает [DOT_START.md](DOT_START.md), второй — [DOT_PEER_START.md](DOT_PEER_START.md). A лично пишет код интеграции и ведёт firmware/hardware; B лично пишет и ведёт Windows-приложение, включая симулятор, файлы и упаковку. После передачи своей области B самостоятельно назначает внутренние задачи. Правила — [coordination.md](docs/coordination.md), редакция 1.2, приёмка — [quality-gate.md](docs/quality-gate.md). Репозиторий: https://github.com/font-weight/stm32_motortester. Статус нового снимка и точные результаты фиксируются в его PR и progress.md.

MVP-01 и Windows-часть MVP-04/06 принадлежат B; MVP-02/05 — A; MVP-00/03/07 совместные с интегратором A. Общая CI и сборка сайта/документа принадлежат A, команды Windows-сборки и содержание справки приложения — B. Семь ролей A не дублируют команду приложения.

Для приёмки нужны действующие независимые вердикты Critic-A/Critic-B применимой области, рубрика и привязка к конкретной проверенной версии; это условие должно быть проверено перед слиянием. Для общих результатов/релиза нужен проходной вердикт обоих критиков, для отдельных модулей — критика направления. Балл не заменяет тесты и аппаратные свидетельства.

## Ближайшие задачи

### HW-001A — паспорт для низковольтного опыта

**Результат:** маркировка MCU/платы, документированные память и допустимые напряжения, доступный программатор, выбранное низковольтное питание и способ получения массива на ноутбуке. Уточнить модель ЛБП и доступность генератора/осциллографа; неизвестные сведения отметить с методом проверки.

**Готовность:** можно составить конкретную схему и задание LV-001 без выдуманных параметров. Катушка, коммутатор и код двигателя не нужны. Паспорт вести в [hardware.md](docs/hardware.md); эта задача не включает прошивку и подключения зажигания.

### LV-001 — первый низковольтный захват

**Зависимость:** HW-001A и известный допустимый уровень источника сигнала. **Результат:** массив отсчётов, файл, график и объяснение шкал.

Проект опыта: один канал, **2048 отсчётов, Fs = 50 kS/s**, 20 последовательных окон по запросу/готовности. Эти значения уточняются по паспорту; они не являются измеренными характеристиками. Фиксированная частота выдачи окон и предыстория в этом опыте не требуются. Для сквозного этапа MVP-03 передача идёт по native USB. Иной способ выгрузки допустим как промежуточная отладка, но он не закрывает проверку USB и MVP-03.

Готовность: 20 окон сохранены без наблюдаемых потерь, дубликатов и ошибок целостности; исходные массивы совпадают после повторного открытия. Постоянный уровень позволяет проверить отсчёты, но не точность времени. Полные критерии, обязательные поля и границы проверки — в [validation.md](docs/validation.md).

### HW-001B — стенд, параллельно HW-001A/LV-001

**Результат:** совместимая пара катушка/коммутатор, документированные ограничения управления, оценка пригодности ЛБП и полная смета. Сравнить доступные варианты по проверяемости состояния образцов, цене и рискам. **Готовность:** рекомендация с основаниями либо конкретный список недостающих сведений; критичные параметры TBD не разрешают включать стенд.

Уточнение двигателя Almera — отдельная задача для будущей автомобильной проверки. Оно не входит в условия завершения HW-001A, LV-001 или HW-001B.

## Критерий завершения дипломного проекта

MVP завершён по критериям [mvp-spec.md](docs/mvp-spec.md): есть согласованные исходники/сборки, приложение, схемы/документация и подтверждённый измерениями рабочий диапазон.
