# I2: почему второй сеанс не получил собственную legacy136

24.10.2026, read-only разбор higher_fs_review. Код, образ и аппаратура не менялись;
новых испытаний нет. Вход — actual SC `build/v6i-fw-01`, результаты `50000/` и
`100000/` в `build/v6i-board-01/`. По сообщению root150k не запускались.

**Причина установлена исходниками: legacy136 рассчитан на одну попытку за boot.**
Это не коллизия generation3. Другая generation при том же boot тоже не исправит
наблюдение. План трёх сеансов без reset ошибочно предполагал повторное вооружение
сохранённого H observer; программный режим выбора Fs сам по себе этого не делает.

## Прямая цепочка

В `source/firmware/platform/mt_stream_diag.h` явно задано `one attempted run per boot`.
В actual `mt_stream_diag.c`:

- `init():60` переводит запись вphase1 только после начального включения/проверки DWT;
  `init():46` отвергает повторный вызов при любом ненулевомphase.
- `begin():64–70` начинает сбор **только изphase1**; новая nonce/generation записываются
  после проверкиphase. Наphase3 функция сразу возвращается.
- `observe():141–144` после штатной quiescence публикуетphase3 через `publish_frozen()`.
- `cycle():33` вphase3 возвращает сохранённый freeze_cycle; новые интервалы не измеряются.
  `active()` также разрешает обновления лишь вphase2.
- В `patched/v2/app/mt_live_runtime.c:95–96` новый START действительно вызывает
  `MT_DIAG_BEGIN(generation,nonce)` перед предварительным quiesce. Вызов присутствует,
  но после первого freeze блокируется самим observer. Переходаphase3→1 нет.

Модуль H/SB и SC побайтно одинаков: SHA256
`8ead5517425c540a7876eaa540edca7205af5c904970e5688aec17b1718251c3`.
Это сохранённая граница измерителя, не новое изменение ADC/packed10/передачи.

## Сопоставление сохранённых данных

Все четыре136-byte файла first/second для50k и100k имеют один SHA256:
`b50707343a7b0bdf9dabf643d8b002f27a436451da81aa364a5a97cbafb0091c`.
Записанная nonce — первая50k `efa84ac39bfa0e52`, generation3, phase3.
Ожидаемая100k nonce — `8a9bedb9515e7bf0`, generation3. Decoder правильно сообщает
`nonce_mismatch`; принимать старые poll/copy/queue/fault поля как100k запрещено.

Отдельный100k probe/wire/fresh-open сообщил PASS, CAPS mode2/Fs100000, а сохранённый
TIM3 имеет CR1=0/PSC71/ARR9. Это согласуется с приёмом и остановкой100k, но не создаёт
недостающую диагностику этого сеанса. Полная физическая приёмка100k по I2 не закрыта;
она не должна превращаться в утверждение об отказе самого100k потока.

## Минимальный следующий шаг без нового образа

Рекомендация — **отдельный boot для каждого следующего квалифицируемого сеанса**
и уточнённый точный план с независимым допуском. Сохранить оба уже выполненных
результата;50k не требуется повторять ради количества. Для недостающей100k проверки
и затем150k: подтвердить Stop/закрытие владельца COM, сохранить прежние свидетельства,
выполнить согласованный root reset/reboot и фактическое USB-переподключение,
затем fresh HELLO/CAPS и один START. После каждого опыта — свои nonce/gen/frozen136
и регистры до следующего boot. Порядок/число новых запусков назначает root в новом плане.

Reset возвращает BSS/инициализацию observer; простое закрытие/открытиеCOM, HELLO
или изменениеgeneration этого не делает. USB-replug нужен также для согласованного
Windows-соединения; его фактическое выполнение фиксирует root, а не offline decoder.
Flash и возврат SB/S4 не требуются для устранения этой причины.150k пока не подтверждены.

Альтернатива для будущего постоянного per-session telemetry — отдельный узкий
контракт rearm перед валидным новым START при доказанной quiescence, с новой
identity и очисткой всех private `last_*`/`have_*`, сохранением первого отказа
и новым exact build/review. Это изменение измерительной семантики; нельзя просто
разрешитьphase3 вbegin, обнулить запись на каждомHELLO или ослабитьnonce decoder.
Для ближайшего опыта такое изменение шире необходимого procedural reset.
