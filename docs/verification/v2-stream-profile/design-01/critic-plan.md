## Закрытые замечания

- F-P01: вместо агрегатного TBD задан каждый из128 uint32 слов, writer и ticket. FG/ISR validity/saturation banks раздельны; единственное shared grant seen-IN поле явно обновляется FG под прежней IRQ-маской и ISR. Второго frozen банка/скрытых helper globals нет.
- F-P02:250мс — целевой checkpoint. Actual end/overshoot выводятся из сохранённых границ; суммы не обрезаются искусственно. Не вернувшийся callback не выдаётся за измеренный максимум.
- F-P03: min32 raw-read **пар** × reads/2 — эвристический индикатор части overhead, не доказанная lower/upper bound и не вычитаемая поправка. Слишком большой индикатор или boundary uncertainty ограничивает атрибуцию, а малый не доказывает отсутствие observer effect.
- F-P04: переданный первичный reason хранится отдельно от ещё нулевого core.first_reason. ACTIVE внутри RX/STEP создаёт synthetic partial ticket2; clipped остаток не смешивается с полными вызовами. Late epilogues после CLOSING не изменяют даже private open flags.

Дополнительно оговорено: IN publication и completion counters принадлежат разным моментам и не обязаны совпадать при пересечении transfer границами окна. Максимум IN-completion gap заменяет избыточный wrapper counter без роста памяти; он не доказывает host stall. Открытых P0/P1 в проекте нет.

## Достаточность и пределы

Состав достаточен для первого причинного шага: можно различить дорогие foreground-фазы, вложенные TIME-проверки, ISR-нагрузку и признаки задержек из-за FIFO/grant/hold. TIME,STEP,USB ISR и grant wall intervals пересекаются; складывать их как независимые доли CPU нельзя. Остаток не становится автоматически затратами TIME или USB. Этот профиль может не различить host scheduling/NAK/PHY; тогда честный вывод — «не установлено», а следующий измеритель выбирается адресно.

Для приёмки реализации ещё нужны точные hooks всех early exits с неизменным порядком старых guards, один узкий lifecycle/partial/wrap/saturation/race набор, exact ELF/map/stack и decoder. Дополнительный static потолок512 включает всё состояние, а не только sizeof record. После этого требуется самостоятельный допуск точного образа/плана и один ограниченный опыт root. Чтение нового профиля — после закрытия COM, два одинаковых frozen dump; невалидность/отказ сохраняются с возвратом S4. Плановый PASS не заменяет ни один из этих шагов.
