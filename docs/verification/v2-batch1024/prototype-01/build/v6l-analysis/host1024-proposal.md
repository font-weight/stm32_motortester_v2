# L: приём пакета до1024 отсчётов — предложение со стороны приложения

## Выбранный первый прототип25.10.2026 — поправка к историческому анализу ниже

Root и автор firmware согласовали **TX-only1336, count известен до отправки**,
wire0.3/mode5, без footer0.4 и без увеличения firmware RX. Прежняя рекомендация
early-streaming/footer в основном тексте ниже остаётся исторической альтернативой;
она не применяется к этому draft. Изменения host разрешены как черновик,
не приняты до независимого ревью/integration; Flash/пакет не входят.

Точный draft-контракт:

- Mode5=config5;150000/1; ADC12/retained10; encoding2; canonical low2zero.
- DATA прежнего layout: header24+metadata20+packed1280+CRC4=1328 raw;
  payload≤1300; wire COBS с delimiter≤1335. TX capacity1336 содержит запас,
  лишний1336-й wirebyte не становится допустимым кадром.
- Discovery0.2 triples(capabilities,max_block,max_payload):
  `(1,128,512)`, `(3,128,512)`, `(7,256,512)`, `(15,1024,1300)`.
- Freshnonce HELLO0.3 mode1/2/5. SelectedACK capability1: modes1…3 max128/
  payload512; mode4 max256/payload512; mode5 max1024/payload1300.
  CAPS5 exact `(5,5,0,12,150000,1,1024,1,10,2)`.
- Public150 требует marker15; SC/SD150 отклоняются до START без fallback.
  Исторические modes1…4 не переопределяются, файлы3/4 читаются прежними.
- Intrinsic `0.3-batch1024-20261025`, acquisition_mode=config5;
  прежние17 полей/magic3/4/companion3. Полное CRC/delimiter до публикации.
- Extended envelope разрешён только device DATA0.3/config5; старые режимы
  и control сохраняют payload512/frame544. Read544, raw256KiB/items1024,
  journal8192 и время20/3мкс не расширяются.

Производственный build нового firmware пока не назначен в host-тестах:
`0xF0102401` — явно синтетический fixture identifier, не проверенный образ.

## Вывод и ограниченный следующий путь

Приложение может принимать один логический DATA до1024 отсчётов, собранный
из нескольких чтений COM. Размер одного чтения544 байта и текущие лимиты
сырой очереди/журнала увеличивать для этого не требуется. Нужны отдельный
согласованный режим, увеличенный ограниченный накопитель одного кадра и
строгая проверка нового формата до публикации отсчётов.

Согласование с автором firmware выявило существенную развилку. Если весь
DATA известен до первого отправленного байта, достаточно нового mode5
и явно объявленного большого payload. Но при экономии SRAM через начало
передачи **до накопления1024** фактический последний count при Stop ещё
неизвестен. Существующий wire0.3 требует точные length/count в начале.
Для предложенного автором потокового кодировщика с конечным count в footer
рекомендую **отдельный wire0.4/mode5**, сохраняя wire0.3/mode4/DATA256
без изменения. Не называть такое изменение простой заменой константы.

Первый ограниченный результат L должен быть единым согласованным byte
контрактом и доказательством ограниченной памяти/владения firmware.
Только после него — изменения обеих сторон. Сам выбор1024 не доказывает,
что устранена причина переполнения SD спустя20,6с.

## Что именно становится больше

Четыре разных величины нельзя называть одним размером пакета:

| Уровень | Для1024 сохранённых10-битных отсчётов |
|---|---|
| Canonical raw приложения | 2048 байт u16le; коды0…4092 кратны4 |
| Плотно упакованные значения | 1280 байт |
| Один логический DATA с COBS/CRC | Больше1300 байт, точный предел зависит от нового footer |
| USB bulk packet / одно чтение приложения | USB endpoint прежний64 байта; одно bounded read приложения544 байта |

Для **гипотетического неизменного layout0.3**: metadata20 + packed1280
=payload1300; header24+payload+CRC4=raw1328; верхняя граница COBS с delimiter
`1328 + floor(1328/254) + 2 = 1335` байт. Это расчёт, не готовая схема0.4.
Если новый footer добавляет F байт поверх этого layout, предел считать
по `raw=1328+F`, `frame=raw+floor(raw/254)+2`; нельзя переносить1335
на ещё не зафиксированный footer. Например, F=4 дал бы1339 байт — только
иллюстрация расчёта, не назначение footer4.

Частота логических DATA снизится с585,9375/с при256 до146,484375/с
при1024. При прежнем layout расчётная верхняя оценка wirebytes/с снизилась
бы с217382,8125 до195556,640625, около10%; количество DATA уменьшится
в4 раза, но количество физических USB-пакетов не уменьшится в4 раза.
Packed samples сами требуют187500байт/с. Footer добавит свои расходы.
Условная оценка ceil(1335/64)=21 не учитывает фактические границы передач
FIFO/control/ZLP и не является измерением USB или ISR.

Полные1024 отсчёта занимают номинально6,826666…мс при150k. Шаг отдельного
отсчёта остаётся20/3мкс. Задержка появления первого DATA зависит от DMA,
начала упаковки и обслуживания USB; её нельзя вывести только из размера
пакета либо timestamp одного host read.

## Почему текущий whole-fit нельзя просто увеличить

K сохраняет FIFO384/maxwrite384 и целиком подготовленный кадр≤371.
DATA1024 целиком туда не помещается. FIFO384 — не максимальный размер
USB потока, но текущий whole-fit writer намеренно не принимает кадр по
частям. Fragmented transport значит несколько принятых частей **одного**
COBS кадра с единственным финальным delimiter, а не четыре самостоятельных
DATA256, переименованных в «пакет1024».

В [actual SD header](../v6k-fw-01/patched/v2/protocol/mt_live_device.h)
rx, previous и tx зависят от общего FRAME_MAX544. Глобальная замена544
на1335 увеличила бы три статических массива минимум на2373байта.
Сохранённая SD имеет лишь916байт сверх8192 stack reserve; такой патч уже
не проходит эту границу. В [wire codec C](../v6k-fw-01/patched/v2/protocol/mt_wire.c)
есть также локальный raw[RAW_MAX], а message содержит payload[PAYLOAD_MAX].
Их массовое увеличение добавит стековые расходы. Нельзя считать только tx.

Очередь8×128 вмещает ровно1024, поэтому ожидание всех8 слотов с их удержанием
до конца большого кадра оставляет нулевой запас свободных слотов в момент
выбора. DMA half512 всё ещё требует обслуживания по прежней границе3413мкс.
Длительность1024/Fs не заменяет эту границу. Автор исследует ограниченный
streaming COBS, передачу владения отдельными128-блоками раньше финального
footer и отдельную границу committed prefix. Его расчёт памяти предварителен;
нужны exact map/stack и модель повреждённого/незавершённого большого кадра.

## Рекомендуемое согласование

Вариант, подлежащий фиксации общим контрактом, а не уже принятые wirebytes:

1. Сохранить прежний HELLO0.2 discovery. Старые пары/лимиты1/128/512,
   3/128/512 и7/256/512 принимаются по прежним правилам.
2. Новый строго определённый marker, например capability15 с новым bit8,
   объявляет поддержку wire0.4/mode5/max1024. Поле max_payload объявляет
   **точную величину нового контракта**, а не произвольные2048. Числовое
   значение зависит от места/смысла footer и пока TBD.
3. Публичный выбор150k в новом приложении требует нового marker и свежего
   **другого** nonce HELLO0.4(mode5). SD/SC150 явно отклоняются до START,
   без скрытой замены mode4/mode3. Старый пакет SD остаётся для возврата.
4. Для50/100k можно сохранить выбранный HELLO0.3(mode1/2) и прежние ACK/CAPS,
   даже если discovery новой прошивки объявляет общий max1024. Общий
   discovery max и выбранный max не смешивать. Firmware compatibility
   modes1…4 сохраняется; не требовать0.4 от неизменных режимов без причины.
5. Выбранные ACK и CAPS mode5 строго связывают revision, config/mode5,
   channel0, ADC12, Fs150000/1, max1024, retained10 и encoding. START
   возможен только после совпадения запроса и наблюдённого контракта.
6. Отдельно закрепить header sentinel/тип DATA0.4, footer actualcount,
   точный CRC domain и порядок CRC/footer/delimiter. Не присваивать meaning
   старому reserved-полю или type DATA0.3 молча.

Важная поправка к реализации host: сейчас connection.protocol_revision
местами выводится из длины CAPS (10→0.3) в
[stream_device.py](../../host/motortester/v2/stream_device.py).
Для нового протокола это недопустимо: сохранять фактически согласованный
revision endpoint, даже если CAPS0.4 имеет те же10 полей. Аналогично ветки
retained_bits и companion binding должны выбирать режим по явному registry.

**Альтернатива без нового footer:** mode5/config5 на wire0.3 с exact
discovery15/max1024/max_payload1300, ACK выбранного mode5 с теми же пределами,
старые modes1…4 неизменны. Она меньше по host-изменениям, но требует знания
length/count до начала и доказанной схемы памяти/владения firmware. В текущей
экономной early-streaming архитектуре это условие не выполнено. Задержать
Stop до набора1024, добавить нули или скрыто потерять partial tail — не
допустимый способ сохранить старый header.

## Ограничения приёмника и публикация данных

Основные места кода:
[wire](../../host/motortester/stream_wire.py),
[endpoint](../../host/motortester/stream_endpoint.py),
[serial](../../host/motortester/stream_serial.py),
[controller](../../host/motortester/stream_controller.py),
[offline verifier](../../host/tools/verify_stream_trial.py).

- MAX_INPUT_BYTES544/SerialPeer.read544 и не более8 насыщенных чтений перед
  yield сохраняются. Endpoint уже накапливает кадр между вызовами receive;
  большой кадр может пройти через3 или больше коротких reads. Границы read
  не являются границами COBS или DATA.
- Нужен новый bounded envelope максимум для0.4 и RX accumulation до него.
  Старые0.2/0.3 пределы payload512/frame544 и per-mode count128/256
  остаются строгими после определения формата. Не увеличивать все пределы
  прежних режимов одной глобальной константой. Предварительный общий
  накопитель может иметь наибольший согласованный cap, но это ещё не
  разрешение большого кадра в старом режиме.
- Новый parser прежде публикации проверяет ограниченную длину/COBS,
  конечный CRC, структурные поля footer, actualcount1…1024, точное число
  packed bytes и нулевые padding bits, nonce/revision/generation/config,
  sequence и first_index. Старую политику nonce isolation сохранить:
  foreign nonce не обходит framing/CRC и не меняет текущий контракт;
  wrong revision текущего nonce — fail closed.
- Только **полный** валидный кадр создаёт ValidatedData/StreamBlock,
  изменяет received_end/CRC и поступает в файл. Появление первых384/544
  байт не разрешает публиковать часть1024. При оборванном footer/delimiter
  сохраняется лишь ранее проверенный префикс. Полнота неизвестного
  произведённого хвоста не восстанавливается из выданных firmware частей.
- Для mode5 full count1024; short1…1023 только последний DATA после Stop/fault
  согласно общему контракту. DATA после short запрещён. END CRC остаётся
  по canonical u16le, а не packed bytes; prefix/index увеличивается на
  actualcount, sequence — на один законченный DATA.
- PARTIAL_MS1000/DATA_MS1000 и handshake byte4096 сейчас не требуют
  увеличения: это отдельные ограничения времени/контроля, а не size cap.
  Иной timing proposal требует собственного основания; большой пакет сам
  по себе не разрешает бесконечное ожидание или отсутствие USB progress.
- Synthetic peer должен выдавать действительно один большой кадр через
  bounded read544, а не увеличивать test read/backlog для PASS. Его
  входящие control-буферы1088 не относятся к device DATA. Текущие2048 байт
  synthetic outgoing queue могут вместить один~1340-byte DATA и обычные
  control replies, но фактическую сумму и fail bounds надо сверить после
  final layout, не увеличивать заранее.

## Файлы, время, калибровка и старые записи

[StreamBlock](../../host/motortester/stream_model.py) принимает до8192 samples;
[journal](../../host/motortester/stream_recording.py) пишет chunks8192.
1024 canonical samples занимают2048байт и уже помещаются в эти пределы.
Очередь host256KiB вмещает максимум128 полных таких блоков при item cap1024;
это131072 samples, номинально0,873813…с при150k. Byte cap не увеличивать,
переполнение остаётся явным отказом. Journal blocks не равны wire frames.

Рекомендуемая новая intrinsic identity — отдельный закрытый marker вида
`0.4-batch1024-<дата-контракта>`, acquisition_mode=config5, Fs150000,
source_adc_bits12, retained_bits10, discarded_lsb2, u10packed_le,
left_shift_2/truncate_lsb, stored u16le/adc12. Точное имя/дата назначаются
в каноническом контракте. Старая пара mode4/`0.3-batch256-20261024` и
mode3/`0.3-modes-20261024` не переопределяются. Mode5 с прежним marker
и новый marker с прежним mode отклоняются, в том числе без companion.

Существующих17 intrinsic fields, magic3/4 и companion3 достаточно, если
не меняются публичные semantics terminal/границы сохранённого префикса:
расширяется закрытый registry, не layout. Companion должен хранить0.4
и проверять selected max1024 по intrinsic mode5; он не подменяет отсутствующие
поля исходного журнала. Старый читатель отказывает на неизвестном marker,
новый читает старые файлы без переписывания. Если streaming firmware требует
нового внешнего terminal/failure meaning, сначала отдельно оценить изменение
формата, а не скрывать его за той же строкой unknown-accounting.

U_CH1=a*code+b, code domain, retained10 и крайние корзины0/4092 прежние.
Калибровка/номинальное время/CSV не должны зависеть от размера DATA.
Индекс/Fs сохраняется с рациональным шагом20/3мкс; JSON/CSV metadata несут
новую identity. Проверьте также regex session_id и decode/partial bound
offline verify_stream_trial: сейчас он знает wire0.[23]/MAX_ENCODED.

## Минимальная будущая проверка после принятия контракта

Не запускалась. Предлагается сохранить четыре существующие host-группы:
negotiation/mismatch, ограниченный codec+read fragmentation+padding/CRC,
intrinsic file/time/companion, чтение старых128/256. Внутри них необходимы
полный1024, один non-byte-aligned tail, short1023, reject1025 и неверный
footer/length/CRC; обрыв большого кадра сохраняет только предшествующий
префикс. Не перебирать все1024 возможных count и не запускать весь suite.

Один actual-C producer fixture full1024+короткий tail+END должен пройти
Python consumer с независимым expected canonical raw/CRC. Один targeted
Windows GUI Record→Stop→fresh Open→CSV с явно synthetic источником,
затем exact frozen package. Ни один из этих результатов не заменяет
отдельный ограниченный аппаратный план после software gate.
