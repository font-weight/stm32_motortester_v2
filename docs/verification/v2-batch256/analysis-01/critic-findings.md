# V2-06k — предварительная независимая критика DATA256

24.10.2026. Критик: `stream200_critic`, не автор реализации.
Область: чтение двух предложений и затронутых границ существующего SC.
Это предварительный разбор проекта, **не формальный contract PASS, не приёмка
кода/образа/Windows-пакета и не допуск Flash**. Балл не назначается.
Production, аппаратные интерфейсы и тесты не запускались/не изменялись.
Записан только этот отчёт.

Предложение **реализуемо как следующий ограниченный кандидат**: объединить
два соседних queue128 в один DATA256 только в новом mode4. Уже передаются
пакеты; меняется их размер, а не вводится оконный сбор с паузами АЦП.
Новый mode/config и явный discovery marker позволяют сохранить wire0.3
без переопределения опубликованного mode3. Обязательного перехода на wire0.4
или изменения структуры journal здесь не обнаружено.

Расчёт подтверждается: 256×10/8=320 sample-байт; payload340;
decoded envelope368; безопасная верхняя граница COBS с delimiter371 < FIFO384.
Глобальные пределы payload512/frame544 и существующий staging достаточны.
Это проверка вместимости, **не доказательство скорости**. При150k число
полных DATA уменьшается с1171,875 до585,9375 в секунду. Фактические USB transfer
boundaries, ожидание свободного FIFO и время guarded commit этим не измерены.

## Границы, которые требуется закрепить в каноническом контракте

1. **Закрытое согласование.** Discovery разрешает ровно пары1/128,3/128,7/256;
   последний максимум глобальный. Selected ACK/CAPS для mode4 объявляют256,
   а для1/2/3 —128. Нельзя разрешать START по одному номеру build или заменять
   всюду общий128 на256. Новый host на SC при выборе150 явно отказывает до
   START, без скрытого mode3 fallback; SC50/100 остаются доступны. Старый host
   должен отклонить discovery7/256 до START. CAPS flags1 и layout END прежние.
   Неподдержанные сочетания, current-nonce revision mismatch и malformed
   envelope остаются отказами; stale nonce игнорируется после bounded checks.

2. **Два блока — одна публикация.** Ticket фиксирует оба выбранных слота,
   count/index и решение объединить, вместе с прежними session/mode/epoch/TIME
   границами. Перед первым изменением CRC, prefix или queue проверяются оба
   блока и непрерывность индексов. Нельзя pop первого при stale втором.
   Полный accepted DATA увеличивает prefix на фактическое count и sequence
   один раз. Known-zero, partial, unknown acceptance, post-write TIME fault
   не превращаются в успешное потребление всей пары. Queue остаётся8×128;
   второй sample-массив не нужен и не входит в scope.

3. **Только конечный short.** STREAMING mode4 выдаёт полные256; lone128
   ожидает следующую публикацию без блокирующего ожидания в foreground.
   ADC/TIME/USB/RX/Stop продолжают обслуживаться. После синхронного
   quiesce/tail append/seal в DRAINING последний1…255 разрешён лишь когда
   исчерпывает сохранённую очередь. После него DATA больше нет. Остаток128
   должен уйти при Stop, не ждать отсутствующую пару. Остаток257 означает
   full256 и final1, а не short128 с последующим DATA. Нули не добавляются;
   неизвестный произведённый хвост остаётся неизвестным.

4. **Старые данные и режимы.** Mode3 остаётся150k/10/128, mode4 —150k/10/256.
   Для mode4 допустим новый intrinsic marker `0.3-batch256-20261024` с
   закрытой неизменяемой таблицей. Пара revision+mode достаточно определяет
   wire maximum без companion. Дополнительное поле max в journal не требую.
   Canonical коды обоих10-bit режимов —0…4092, кратные4; CRC по u16le,
   время index/Fs, не по packed-байтам или числу кадров.

5. **Wire и journal имеют разные границы.** DATA count ограничивается
   согласованными128/256. Journal уже может агрегировать8192 кодов и не обязан
   сохранять wire boundaries. Нельзя вводить per-wire cap256 в reader старого
   журнала. Новый marker допускается строгой валидацией без необязательных
   default-полей; старые markers/magic/companion не переписываются. Открытие
   без companion сохраняет mode4 и quantization, с companion проверяет
   observed CAPS против intrinsic таблицы.

6. **Область производительности не расширять.** ADC/TIM3/DMA, rational150k,
   deadline3413/CEN boundary, H runtime/USB burst6/<500us, TIME и очереди
   остаются прежними. J TIME-specialization не объединять с K. Более длинный
   prepare может состарить ранний USB quantum, а CRC512 canonical bytes
   увеличивает одну guarded transaction. Это открытые ограничения до
   измерения, не повод заранее ослаблять guards или удваивать grant.

## Конкретные места риска существующего SC

В `host/motortester/stream_wire.py` общий MAX_BLOCK128 применяется и к
packer, и к count admission. `stream_endpoint.py` устанавливает `_short_seen`
через этот общий максимум. Поэтому изменения одного decoder недостаточно:
при mode4 count128 должен быть терминальным short, count256 — полным.
Тот же предел нужен synthetic peer и offline physical verifier.

`stream_model.py` признаёт quantization только через прежний MODE_REVISION
и `mode==3`; эти условия нельзя оставить для нового mode4. При этом
MAX_BLOCK_SAMPLES8192 относится к хранению и менять его не требуется.
Новый DATA256 создаёт512 raw-байт: существующий byte cap256KiB остаётся
тем же, хотя число помещающихся full-DATA элементов уменьшается.

В actual SC core `completed(DATA)` проверяет и снимает один head. Новый
двухслотовый путь требует предварительной валидации всей пары; добавление
второго независимого pop после первого не доказывает атомарность отказа.
Queue — single foreground owner, но borrowed views и transport epoch
по-прежнему имеют разные времена жизни. Замена HELLO или Stop при уже
частично принятом DATA не должна переименовывать/отбрасывать его префикс.

## Только необходимые будущие свидетельства

- Одна actual-core/queue/wire модель изменённого pair path: full256;
  кольцевой переход7→0; stale второго слота до любых CRC/pop; known0,
  partial/unknown и прежние TIME/epoch ошибки; Stop/HELLO при pending frame;
  конечные остатки1/2/3/127/128/129/255 и257→256+1. Это сценарии одной модели,
  а не приглашение повторить весь унаследованный набор. Сохранность старых
  guards подтверждается адресным source comparison.
- Компактная host-проверка negotiation/selected max и несовместимых peers;
  независимые packed vectors129/255/256, отрицательные257 и mode3/count129,
  padding; actual C→Python DATA256+tail+END/CRC; mode4 journal fresh Open
  без companion и точное canonical равенство. Прежний mode3 journal остаётся
  читаемым; не требуется заново весь набор исторических файлов.
- Exact ARM/static для нового образа и metadata: SC SRAM/stack не переносить
  автоматически. Новый view/ticket не должен незаметно добавить sample buffer.
  Один адресный Windows GUI/package flow Record→Stop→Open проверяет изменённый
  размер и provenance; обычные старые UI сценарии не повторяются без причины.
- Затем отдельный допуск exact hardware plan и независимое physical review.
  Legacy136 остаётся one-attempt-per-boot: Reset/Run и фактическое
  USB-переподключение перед каждым диагностируемым сеансом. Старый I3 FAIL
  сохраняется; успешная модель/упаковка не подтверждает150k на плате.

## Небольшие уточнения авторам перед pin

Host-фразу «Больше задержка первого полного кадра» следует смягчить:
DMA half512 публикует несколько queue128 за один проход, поэтому нужная
пара может уже находиться в очереди. Интервал256/Fs не доказывает увеличение
первой задержки. Требуется указать зависимость от DMA/очереди и измерения.

Firmware-фразу о запрете расширения «wire/file режимов» следует отделить от
journal chunk8192, как уже сделано в host proposal. Это точность документа,
а не требование нового формата хранения.

Предварительное сомнение о названиях прежних capability bits снято после
перечтения принятого canonical §3: STREAM_BASE и REQUIRES_MODE_HELLO_0_3
уже закреплены. Их сохранение допустимо; отдельный CAPS flags1 не получает
новой семантики. Существенных противоречий между двумя K предложениями
после перечисленных уточнений не обнаружено. Формальное заключение будет
привязано к единственному окончательному каноническому контракту.
