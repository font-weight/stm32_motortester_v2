# Подготовка следующего DATA1024 после завершения предыдущего

Ограниченная гипотеза Q: при завершении передачи предыдущего пакета
освобождённый буфер можно сразу использовать для следующих отсчётов.
В SI обычная сборка нового пакета стоит после следующего обслуживания АЦП.
Поэтому очередь может переполниться раньше, чем программа начнёт её читать.
Основание и ограничения — [сохранённый разбор P2](verification/v2-progress-identity/followup-01/analysis.md).
Фактические результаты и установленная версия находятся только в
[progress](progress.md). Это описание алгоритма, не подтверждение150k.

## Граница изменения Q/SJ

Дополнительный collect-only выполняется после успешного последнего write
**уже подготовленного полного** mode5 DATA1024, прежнего USB flush и свежих
проверок времени/связи. Последний cached проход ещё не собирал новый пакет:
полный кадр длиннее максимального write384, поэтому он не мог завершиться
первым write. Дополнительные максимум512 отсчётов сохраняют прежний предел
collection на проход, но увеличивают время конкретного cached прохода.

До чтения очереди проверяется сертификат фактически опубликованного
завершения: старый ticket DATA/READY1024 с offset>0, те же nonce/generation/
revision, ожидаемые prefix/CRC/sequence и новое состояние EMPTY/tx0.
Одного успешного return недостаточно: он возможен и без write.
Новые Stop/HELLO/control/error, sealed queue, RESERVE/exhaustion и смена
identity запрещают prefetch. Modes1–4 сохраняют прежнее поведение.

Общий helper переносит до четырёх блоков128 из очереди в существующий
packed staging. Проверки views/индексов/канонических кодов и atomic pop_many
сохраняются. Локальный work-copy публикуется после успешного pop.
Новый буфер не выделяется. При queue0 ничего не начинается. В этом месте
нет seal, frameCRC/COBS, дополнительного write/grant или остановки АЦП.
Global accepted prefix/CRC и sequence повторно не продвигаются.
Packing и локальный prefixCRC всё же требуют вычислений; это не простой memcpy.

## Время, обрыв и остановка

Collect выполняется вне write IRQ guard, с текущим app actor. До и после
нужны fresh TIME, epoch/soft serial, loss/stable/usable. ISR может изменить
transport epoch, но не core/queue. Устаревший диапазон удаляется прежним
cleanup, не восстанавливается в освобождённые слоты и не попадает в новую
сессию. Ошибка collection получает новый текущий ERROR ticket; повторный
guarded step допускается только для recovery, без второго DATA write.

Stop после prefetch завершает owned-but-unpublished диапазон обычным drain.
HELLO при offset0 отбрасывает старый staging. Первый диагностический close
предшествует cleanup, frozen запись не изменяется поздними завершениями.
Прежний prepare-span включает и prefetch; сумма остаётся inclusive-временем,
а не чистой загрузкой CPU. ABI64/136 и общий generated build id сохраняются.

Прежние flush-попытки сохраняются до collection, но они не гарантируют,
что USB transfer уже начался. Новая работа может задержать следующий ADC
poll; deadline3413мкс и grant6/<500мкс не расширяются. Static growth должен
быть нулевым, exact stack — проверенным с новым helper. Ни число итераций,
ни программная модель не доказывают достаточное время на плате.

## Критерий ограниченной программной готовности

Одна адресная actual-core/runtime-boundary модель должна проверить успешный
completion→flush→collect, ownership/CRC, отказы и отмену по epoch/TIME,
Stop/HELLO, отсутствие второго write/grant и активный observer с exact SJ ID.
USB/MMIO/clock seams и synthetic legacy setup явно отделяются от actual C.
Затем exact ARM/resources/source review и независимый критик≥9,5.
Незатронутые ADC/DCD/TIME/wire сохраняются, широкие старые suites не нужны.

Аппаратный опыт допускается отдельным точным планом после backup/readback
и нового фактического USB-replug. Один запрос150k/30с должен завершиться
без source fault/gap, с согласованными raw/CRC/Open/END/ACK и остановкой.
При отказе сохраняются данные и установленный образ; старую прошивку
автоматически не возвращать. Программный PASS не закрывает stable150k.
