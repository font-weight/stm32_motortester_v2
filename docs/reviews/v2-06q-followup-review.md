## Почему узкий замер обоснован

Первый Q2 снимок пригоден: READY1024, offset1152/1335, queue8, FIFO free64, held/deferred, task-not-ready. Последняя часть183байта не проходит whole-fit при64 свободных: дефицит119байт. Очередь переполняется внутри ADC service до grant/TX данного прохода. Это объясняет место backpressure, но не различает последний intermediate TIME/budget hold, final completion/task turnover или ожидающий обслуживания текущий transfer. Поля снимка не записывают последовательность этих причин.

Данные не обосновывают безусловный перенос grant перед ADC. Сумма2952+500=3452мкс — лишь отсутствие консервативного запаса относительно3413, **не измеренная длительность конкретного прохода**;500мкс дополнительно не является WCET handler/всего grant. Частичное принятие64 вместо183 также не освобождает staging и само по себе не доказывает улучшения устойчивого темпа.

Прочитаны соответствующие ветви exact SJ `dcd_stm32_fsdev.c`, current progress close/snapshot и сохранённый `build/v6f-board-01/profile-time-analysis.json`. Старый F2/S9 действительно имеет grant26/15,16publications,76IN packets,59resumes,16final и1time hold. Но это100k/DATA128 с512B observer и иным расписанием; cumulative counters не восстанавливают current-transfer Q2. Их можно использовать как пример приёма «первое фактически вычисленное false», но не как доказательство нынешней причины или долей времени. Повторный offline пересчёт старых записей не создаст отсутствующие transfer/age поля.

Предлагаемый last-transition bank лучше нового изменения расписания без диагноза, **если** он даст актуальное, привязанное к transfer наблюдение с явным unknown, а не только новое число held. Последующий аппаратный результат должен оцениваться по пригодности замера, не по увеличению числа пакетов.

## Один собранный список решений до implementation

1. **Значение current transfer и актуальность причины.** Зафиксировать момент успешной публикации CDC-IN, serial/cookie, active-window binding и насыщение без wrap/reuse. До первой наблюдённой публикации transfer неизвестен: поздний completion прежнего control не получает вымышленную новую identity. Новая публикация, cancel/reset/lifecycle должны явно инвалидировать применимость старой причины. Одного cookie недостаточно: в том же transfer новый grant может снять TIME hold, а OUT/SETUP/другой IRQ затем вновь удержать обработку. Нужны либо invalidation/applicability на этих переходах, либо честное значение **historical last CDC decision**, которое декодер не называет причиной текущего held. Это главный семантический риск проекта.
2. **Только реально вычисленная ветвь.** Закрепить enum первого фактически отказавшего условия и отдельные состояния publication/waiting, resume, final и unknown/other. Не вычислять заново short-circuit MMIO/TIME predicates, не переставлять рабочие чтения и не достраивать downstream причины, до которых исполнение не дошло. Для age/budget/total/queued определить момент снимка: до или после packet handler. Если TIME не проверялось или таймер недостоверен — sentinel/validity, а не условный ноль. `queued==total` означает загрузку в PMA в соответствующей фазе, не автоматически доставку host или завершение transfer. Publication attempt, успешная публикация и actual completion должны различаться.
3. **FG/ISR ownership и freeze.** До кода нужна таблица writer/guard для каждого поля и всех invalidation hooks. Foreground публикация под существующим guard, ISR updates при закреплённых условиях вложенности; `volatile` не делает многословную запись атомарной. Запрет поздних записей должен действовать с N ACTIVE→CLOSING, включая update, начатый рядом с freeze; ISR не должен изменять flags64 через конкурирующий read-modify-write. Указать порядок publication validity/frozen и memory ordering. Сохранить один bank, без скрытой второй копии/глобального счётчика. Равные два SWD dump сами по себе не доказывают отсутствие гонки.
4. **Область и время наблюдения.** Связать новый bank с exact generated build и тем же nonce/gen через64/136 без старой независимой build-константы. NO_ACTIVE/UNAVAILABLE не получают историю, saturated serial не выдаётся за уникальный. N CAP≈250мс — тоже first close; замороженный CAP bank не описывает более поздний queue fault. Зафиксировать DWT modulo/age wrap/invalid clock и возможный skew между последней transition, cause latch и последующим USB snapshot. Не обещать одновременность всех полей64/136/newbank или причинность одного held только из совпавших копий.
5. **Ресурс и влияние измерителя.** Лимит≤24байт относится ко **всей** новой static памяти, включая alignment, private fields и counters. Сейчас reserve8192 оставляет28байт; предполагаемые4байта после добавления24 — расчёт до exact link, не уже подтверждённое размещение. Нужны `sizeof/offsetof/alignment` и итоговые map/stack/ISR frame. DWT reads/stores/branches измерителя меняют работу gate; запрещены новые TIME-health loops, dispatch/flush/grant/ADC_DR и изменение6/<500. Нельзя вычитать observer overhead как точную поправку или объявлять успех измерительного образа qualification исходной SJ. Если корректность/достоверность не помещается, проект пересматривается до интеграции; расширение RAM или512B profile не следует из этого review.

Это обязательства к ещё не определённому контракту, а не найденные дефекты уже существующего нового кода. Старые Q1/Q2 отчёты остаются неизменными. Вводить все эти состояния как отдельные большие счётчики не требуется: автор должен выбрать минимальное представление с достаточной validity, либо сократить заявленный вывод.

## Минимальные свидетельства следующего узла

До реализации: frozen ABI с offsets/widths/sentinels/owner, список exact hooks и evaluated branches, lifecycle/first-close/current-transfer applicability matrix. Только затем можно оценить пригодность узкого implementation-контракта. Черновой design сейчас допустим.

После реализации достаточно одного ограниченного actual-C runner со следующими группами:

- publication→intermediate resume/hold→final; одинаковые total/queued у разных serial, новая публикация и same-transfer regrant/other-event invalidation, unknown до первой публикации, saturation;
- только first evaluated branch с сохранёнными порядком/числом рабочих volatile reads; timer/not-evaluated/age-wrap cases и честный unknown;
- FG/ISR update около CLOSING, неизменность frozen, CAP/NO_ACTIVE/UNAVAILABLE, matching exact build и64/136 binding. Явно отделить логическую модель interleaving от actual ISR execution.

Source equivalence должен доказать прежние gate decisions/6/<500/transfer schedule, а exact ARM — лимит памяти и стек. Это не просьба повторять старые ADC/serializer/GUI suites. Новое аппаратное действие потребует отдельного точного плана; одни ABI/native/ARM не доказывают throughput.

**Итог:** направление диагностики обосновано; безопасно продолжать только ограниченный draft design. Для принятия конкретного ABI/интеграции перечисленные решения ещё обязательны. Физическая цель stable150k и неизвестная причина начального USB Code43 не объявляются решёнными. COM/SWD, тесты, сборки и implementation edits критиком не выполнялись.
