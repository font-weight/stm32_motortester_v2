# V2-06f2 — независимое ревью диагностического результата S9

**PASS, 9,57/10 — только получение и проверка профиля первой ошибки. Физический поток 100 kS/s завершился FAIL и остаётся непринятым.** Цель F2 заранее была диагностической: один START, целевой Record 1 с, наблюдение до первой причины либо checkpoint 250 мс и обязательный возврат S4. Она не требовала превращать прежний отказ в успешный поток. Порог исходной приёмки 100/200 kS/s не изменён; A/C/D/E остаются REWORK.

Критик `stream200_critic` не автор реализации, декодера, физической процедуры или offline-разбора. COM/SWD не использовал, новых записей не запускал; проверял сохранённые первичные файлы и точные исходники.

## Лично проверенные факты

В Windows 10.0.19045/Python 3.14.7 выполнена адресная read-only проверка: все 57 исходных/архивных пар побайтно равны, SHA/размеры совпали; 20 исходных файлов из offline-разбора сохранили свои хеши до и после личного чтения. Сохранённый readback всех 38924 байт совпал с разрешённым BIN.

Повторно разобран `traffic.bin` через существующий parser и проверен порядок: ровно один START, build S9/CAPS100000/1 до него, nonce `98401a74a29ed72a`, generation 3. Получено 23 DATA по 128 кодов: полный префикс [0,2944), 5888 байт. Последовательности и индексы непрерывны, CRC32 3120963445 совпал с END. SHA raw `84b1ed56b65007751d10ea45e9cd0b3e1707eff12a0a7be1eb1b837804d05521`.

END sequence 27, reason 1, flags 3 пришёл **до** host STOP request 4; STOP_ACK sequence 28 подтверждает terminal 27. Это отказ источника, а не обычная остановка по команде. Record продолжался 0,0201285 с и не прошёл целевой 1 с. Полученное число кодов не является свидетельством устойчивого темпа или отсутствия потерь.

Свежий `open_verified_context` и `verify(run)` проверили companion и весь выбранный raw [1664,2944): 1280 кодов/2560 байт побайтно равны соответствующей части wire, SHA `6b128110b81ce2b7583865c4ae23641f06e85c75dfb743780f1b9678f9943513`. Recovery issue отсутствует, discarded tail 0, причина source_failure и неизвестный produced/loss сохранены.

Лично повторён in-memory decode двух 512-байтных и двух 136-байтных файлов; результат полностью совпал с сохранённым. Profile SHA `c95849db9c2e1eb9ed65f2a87275cef0d85764686ee1258478a337d8a8d56396`; legacy SHA `02b958f0bf929a694015b63432654fcf0d7e6b18906356ebba3553ef88406615`. Build/nonce/generation совпали с wire, epoch 3 — отдельное поле профиля, отсутствующее в wire. Profile FROZEN, fg_flags 56 — initial/partial признаки, irq_flags 4 — HAVE_IN; invalid/saturation не установлены. Legacy flags 4 фиксирует first fault, не отказ DWT.

Отсутствие SWD/debug-halt во время приёма, независимые вызовы чтения, время команды 0,7414755 с и пользовательские replug подтверждены сохранённым `hardware-procedure-facts.json` исполнителя. Критик не наблюдал их лично; равенство дампов не заменяет эти внешние факты. При данных условиях интерпретация короткого DWT-интервала допустима; время рассчитано при номинальных 72 МГц.

Противоречия между first snapshot и поздним wire нет: окончательные 2944 кода включают ещё 1024 кода, отправленных при завершении. Нельзя использовать окончательный счётчик вместо 1920 committed до first close. ADC fault 0 также не доказывает известное число реально произведённых/потерянных отсчётов.

Максимальный интервал IN completion 5,449125 мс может включать START_ACK → первый DMA-полублок 512 кодов (номинально 5,12 мс); это не доказанный host stall. Поздние legacy poll 1519 мкс/copy 179 мкс относятся к иной области наблюдения и не заменяют активные фазовые данные. TX_ZERO измеряет всю core-транзакцию с проверками времени и не различает новый encode от повторной передачи уже подготовленного кадра.

Профиль и исходник runtime подтверждают, что вся `mt_live_device_step` проходит под guard. Предложение сократить эту область имеет предметное основание, но единственная корневая причина и ожидаемое улучшение **не доказаны**. Существующий `build_tx` изменяет состояние и может вызвать recovery; его нельзя просто назвать чистым и перенести без отдельного контракта. Следующее изменение требует собственного scope и проверки epoch/deadline, ownership подготовленных данных, post-write/commit и отказов. Настоящий отчёт не принимает такой код и не разрешает следующий Flash.

## Завершение опыта и возврат

Исходный receipt подтверждает cleanup_finished и final phase closed. Лично декодированы сохранённые TIM3/ADC/DMA/RCC бинарные блоки: CEN=0, PSC=71, ARR=9, ADC_CR2=0, SMPR2=4, DMA EN=0; нужные clocks включены, reset отпущен. ADC_DR не входит в сохранённый диапазон. Это состояние после закрытия COM, не подтверждение непрерывности АЦП.

Все 65536 байт rollback-readback равны свежему backup S4, SHA `95d3a11f8db843e362b2c59ed6fbf380dd630e067fa23f6ae5a9c7d2b11dff1e`. После подтверждённого replug READY сообщил S4/50000, ноль отсчётов, no_source_started=true и owner_closed=true. Фактическое состояние платы — S4. Новое пожелание пользователя не возвращаться автоматически после каждого будущего опыта получено после этого уже выполненного возврата; F2 исполнен по своему заранее принятому плану.
