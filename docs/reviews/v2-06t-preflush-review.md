Отказ закрывает пробел [S follow-up](v2-06s-followup-review.md) выбором **не реализовывать** гипотезу. Exact SL source-цепочка лично прочитана в том ревью, её пины сохранены в [critic-followup.json](../verification/v2-postcopy-handoff/critic-followup.json):

1. `tusb.c:425–434` автоматически отправляет FIFO при count≥64; BUSY/CLAIMED запрещают новый claim.
2. CDC имеет `xfer_isr=NULL`: final IN ISR не делает endpoint доступным для нового foreground flush. Пока completion не обработан task, BUSY остаётся.
3. `usbd.c:842–862` снимает BUSY и сразу вызывает CDC callback; `cdc_device.c:515–523` отправляет buffered FIFO или рассматривает ZLP. Weak TX callback пустой, собственного SL override нет. Runtime не вклинивается между этими foreground действиями.
4. В S task уже выполнен до выбранного handoff. При наблюдённом остатке183 нехватка места означает FIFO>201, то есть ≥64: исключение с малым неотправленным FIFO этот случай не объясняет. Другой producer, submit failure или teardown не могут молча подменять healthy исходный путь.

Поэтому новый preflush не добавляет обоснованной возможности публикации в рассмотренном здоровом пути. Поздний FIFO384 и historical RESUMED не опровергают этот вывод и не доказывают причину S2. Произвольно заданный BUSY0/FIFO320 не является достижимым положительным witness. Условие возврата к гипотезе — конкретный source counterexample, а не новый аппаратный опыт или удобный stub.

Предел вывода соблюдён: возможные затраты времени дополнительного вызова не измерены; универсальная невозможность всех ошибочных/изменённых состояний не доказывалась. Изменение лишь задержки не подтверждает предложенный механизм. Сохраняются S2 REWORK6,375, открытая P1-M2-01 и остановленная SL.
