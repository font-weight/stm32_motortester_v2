# Правила разработки Мотортестера V2

Это учебный диплом по электронике и телекоммуникациям; автор впервые работает с Data Science. Общаться и объяснять по-русски. Пользовательские указания имеют приоритет. Рабочий репозиторий — `font-weight/stm32_motortester_v2`; исходный `font-weight/stm32_motortester` только для чтения. Прежнее владение файлами Dot A/B не ограничивает работу в V2.

## Перед работой

Прочитать `README.md`, `task.md`, `requirements.md`, `docs/decisions.md`, `docs/progress.md`, `docs/quality-gate.md`, затем документы текущего узла. При параллельной работе — `docs/coordination.md`. Исходные материалы — `docs/design/`; требования TXT ред. 5, особенно 4А, имеют приоритет над макетами ред. 4. Исторический `docs/mvp-spec.md` читается при затрагивании приборной части вместе с `docs/legacy-notice.md` и не заменяет требования V2.

Текущий объём: один CH1, два UI-профиля, В/мВ на разъёме, Windows 10, STM32F103C8T6/внутренний АЦП/native USB как аппаратная основа. ML, второй канал, внешний запуск и пересчёт в кВ не входят. Не предполагать существование аппаратуры/измерений по наличию схем или демонстрации.

## Итерации и проверка

1. Одна итерация — ограниченный результат с входами, зависимостями и критерием готовности из task/progress. Обычные обратимые решения выполнять самостоятельно; не расширять задачу до всего прибора.
2. Параллельным агентам задавать непересекающиеся области записи. Основной агент проверяет совместимость. Один независимый критик V2, не автор реализации, оценивает точное состояние по `docs/quality-gate.md`; порог ≥9,5/10. Отсутствие оценки/обязательного свидетельства блокирует приёмку результата, но не черновики или независимую работу. Старые два firmware-критика не нужны для GUI V2.
3. Только необходимые проверки изменённого поведения. Для документов достаточно согласованности, ссылок и расчётов. Не запускать весь унаследованный набор и не создавать формальные тесты ради количества.
4. Разделять доказательства: документация/расчёт, программная логика/ДЕМО, GUI в указанной ОС, Windows-пакет, низковольтный сигнал, зажигание, автомобиль. Прохождение одного не заменяет остальные.
5. Сохранять пользовательские материалы, исходные данные и неудачные результаты. Обновлять требования/решения/прогресс. Завершать коротко: что изменено, как запустить, чем проверено, что не подтверждено, что пользователю сделать дальше.
6. Перед push проверять origin: только V2. История и авторство сохраняются; без force-push или публикации в исходный проект. Ветки/commits/разрешённые публикации — в рамках задания пользователя.

## Инженерная добросовестность

Различать первичный факт, условие пользователя, расчёт, предложение и измеренный результат. Для неизвестного писать TBD, способ определения и этап, до которого оно нужно. Максимум datasheet не характеристика готового прибора; проверять корпус/режим/ревизию/errata/питание/источник/интерфейс. Blue Pill не гарантия MCU. Двигатель Nissan не определять по году и примерному объёму. Ссылки/основания — в `docs/sources.md`, действующие V2-решения — в `docs/decisions.md`.

U_ADC, U_CH1 и величина внешнего датчика различаются. Единственный пересчёт `U_CH1=a*code+b`; неизвестный вход — unconfigured, номинальная шкала не калиброванная. Имя/профиль UI/положение графика не меняют raw и физическую калибровку. Не вычитать DC автоматически. Порог/единицы/отрицательный gain/насыщение обрабатывать явно. Аппаратный DC-вход — отдельная задача `docs/hardware-input.md`.

## Данные и объяснения

Сохранять исходные отсчёты, время, разрывы, происхождение и снимок профиля. Анализ не меняет оригинал. Пауза просмотра не Stop записи; оконные паузы не непрерывный поток. Потерянное окно не отсутствие разряда. Качество данных, электрический отклик, независимое наблюдение разряда и состояние катушки — разные сведения. Событие не цилиндр; Δt не автоматически горение.

Будущие данные разделять по физическим объектам и сеансам; не обучать нормализацию/пороги на проверочных данных и не ставить метку неисправности по предсказанию своей модели или словам продавца. Две иллюстрации не независимый обучающий набор. Начинать с понятных признаков и правил, ограничивать выводы проверенными условиями.

В нетривиальном коде объяснять физический смысл, единицы, формы массивов и ограничения, не комментировать очевидное. Для обработки показывать исходный и обработанный результат. Термины — `docs/glossary.md`.

## Документы и аппаратные границы

Одно основное место на вид сведений: требования — `requirements.md`; текущая задача — `task.md`; решения — `docs/decisions.md`; фактический статус — `docs/progress.md`; расчёты — `docs/architecture.md`; методика — `docs/bench.md`; данные/метки — `docs/data-plan.md`; физическая приёмка — `docs/validation.md`; бюджет — `docs/budget.md`. Не размножать текущий статус.

Не связывать независимые задачи: катушки/двигатель не нужны для UI/ДЕМО или первого допустимого DC-опыта. Бюджет ≤100 000 KZT; цены/совместимость/доставку проверять перед закупкой. Не задавать универсальный dwell и совместимость коммутатора/катушки. Развязку проверять со всеми цепями питания/USB/отладки/контрольного прибора. Высоковольтный стенд требует физических условий из validation; программный балл их не закрывает.

Команды запуска нового UI — в `README.md` и `host/README.md`; фактически выполненные проверки — только в `docs/progress.md` и отчёте критика.
